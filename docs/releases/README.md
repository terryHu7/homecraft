# Engine release process

Publish shared engine updates from `terryHu7/homecraft`. Users fork and clone the repository as usual, then use official releases for subsequent updates. Forks do not need to publish releases.

1. Finish the scoped change on a branch. For an engine release, update `package.json` and the lockfile version, then run `node tools/engine-manifest.mjs <version>`. Keep the existing baseline snapshots in Git history. Write concise English release notes in `docs/releases/v<version>.md`; obtain the maintainer's confirmation of public wording before publishing.
2. Run `npm run check:pr` and the normal desktop/mobile browser check. Test the actual initial fork and the previous release, custom core conflicts, old mailbox HTML, and the packaged standalone command. Check the actual experience on a phone before publication. Review the diff, PR title and PR description, keeping personal content out of the release.
3. Commit and open the reviewed PR. Wait for PR title, Listing request and Checks before squash-merging with the PR title. After merging, tag the verified main commit as `v<version>` and push the tag.
4. Run the **Prepare engine Release** Action with that tag. It checks out the exact tag with full history, runs the checks, validates version and manifest, builds `homecraft-engine.json`, a dependency-free `homecraft-updater.tgz`, and `SHA256SUMS`, then creates a **draft** Release. It does not publish automatically. The JSON contains the target engine, recognized official historical hashes, valid baseline snapshots for conflict reports, and the marked Agent instruction block. Local `npm run release:prepare -- --allow-dirty` is for preview only; its bundle is marked as a preview and cannot be installed through the online Release path.
5. Review the draft notes/assets and publish after confirmation. From a disposable initial fork, run the exact public standalone command with `--check`, then update and preview it. Test `npm run update -- --check` from a new clone. Verify that the GitHub latest-Release API exposes the engine asset's SHA-256 digest, the printed backup works, and the redeployed site behaves correctly before reporting publication complete.

Keep the asset names unchanged so old entry commands continue working. Do not point upgrades at moving `main`, a fork's Releases, the site directory, or a CDN-hosted runtime. Old sites keep their own deployed code until their owner updates and redeploys. Future format-breaking updater changes must retain an understandable failure path for old commands.
